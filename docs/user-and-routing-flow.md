# 用户与上游路由流程

## 用户端

1. 用户注册并登录。
2. 在兑换页兑换管理员发放的余额或并发兑换码。余额按网关统一的 USD 计费。
3. 在“密钥”页创建 Key，选择可见分组，填写名称；创建成功后可在密钥列表复制完整 Key。
4. 复制网关端点、Key 和分组支持的模型，直接配置到 OpenAI/Anthropic 兼容客户端。
5. 用户可以随时停用、删除或轮换自己的 Key；删除和轮换不会影响其他用户。

公开分组对所有用户可选，私有分组只有管理员授予的用户可选。服务端会再次校验分组权限，不能只靠浏览器隐藏来保证权限。

## 管理端

1. 在“上游”页填写名称、裸根端点、Key 和成本倍率。保存前会读取真实 `/v1/models`，保存后的 Key 永不回显。
2. 点击模型读取、连通性检查、余额刷新或 `hi` 测试，结果会记录延迟、稳定性和错误类别，不把上游响应原文或凭据返回给客户端。模型读取成功后会把有界的 `/v1/models` 能力快照保存到上游记录；失败刷新保留上一份可用快照并显示错误，修改端点或 Key 时自动清空旧快照。
3. 在“分组”页点击创建分组，选择账号池或上游池。
4. 上游池模式下勾选多个上游；系统读取这些上游的模型，管理员勾选要开放的模型，并为每个成员设置优先级、权重和并发上限。
5. 选择公开或私有、设置价格倍率后保存。新建上游池分组时，分组策略、模型白名单和全部成员在服务端同一事务提交，任一校验或写入失败都不会留下半成品。编辑/切换路由仍保持“先让目标路由可用，再清理旧成员”的顺序。

## 调度规则

- 先按请求格式和分组模型白名单过滤。
- 上游池按已确认的上游模型能力过滤；分组没有显式白名单时使用所有启用成员的模型交集。尚未读取过模型的旧上游保留兼容路由，首次读取后即按快照收敛。
- 上游池按优先级分层，数字越小越优先；当前层没有可用成员时才进入下一层。
- 同一优先级内使用加权轮询，权重越高获得的请求比例越高；序列有上限且每个成员至少保留一个槽位。
- 每个成员独立维护并发槽和短时熔断。429、5xx、网络错误会暂时冷却失败成员，下一次尝试排除本请求已经失败的成员。
- 请求结束、流式中止、协议转换失败和快照重载都释放原来占用的槽位；即使成员在请求期间被删除，也会通过原快照引用正确释放。
- 账号池模式沿用原有账号调度、额度、规则和协议转换逻辑，不会把上游成员伪装成账号扣除账号额度。

## 故障处理

- 上游端点、Key 或模型发生变化时，先在“上游”页更新并测试，再把它加入分组。
- 读模型失败时不要把空白列表当成“全部模型”；重新读取成功后再勾选开放模型。
- 分组保存失败时先刷新列表确认最终状态，再重试，避免重复创建同名分组。
- 运行中的服务、Docker、代理端口和共享网络不由控制台保存操作自动重启；升级或迁移应先在空闲端口做影子验证。
